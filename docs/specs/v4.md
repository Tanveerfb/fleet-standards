## Goal

The standard stops being one 69 KB file that every project loads in full every turn. It
becomes a **core** every project loads, plus **profiles** and **topic files** a project loads
only when they apply. The same release takes the fourteen open proposals and the lessons of
the 11–12 November token attack.

**It deliberately does not:**

- rename or renumber any section. `§GIT` still means `§GIT`; only the file it lives in may
  change. No project has to rewrite a reference
- change what a rule says while moving it. Moves and wording changes are separate commits
- add a Unity or Unreal profile. The game profile is written from one Godot project; others
  are read "in spirit" until a real project proves the wording
- re-audit any project. Each project syncs when its owner next works in it
- set a hard size budget that fails CI (declined 2026-10-21, and not re-opened here). It
  records sizes so the trend is visible

### Motif previews (the owner's proposal, 2026-11-12)

Today `design-motif` Step 3 offers four ways in, all in words, and the first thing the owner
sees is a mockup of the one motif already picked. Two additions:

- **"Show me", a fifth way in.** From the brief, the agent picks three or four candidate
  families (it says why each qualified) and drafts one page of **sample tiles**: each tile
  is one motif applied to the same small set of pieces, using this project's own name and
  words: a heading, a paragraph, a button, a card, an input, in light and dark. The owner
  picks one, asks for another round with different candidates, or switches to any other way
  in. None picked is a normal outcome, not a failure: redraft. The pick then continues at
  Step 4 (variant) and gets its full mockup in Step 5 as now. Tiles are drafts: they live
  in `public/_mockups/` (or an artifact when the owner is on a phone) and are never recorded
  as the locked design. Values in a tile are illustrations, not tokens (§DESIGN: tokens come
  from the locked mockup).
- **A static gallery**, `standards/motif-gallery.html`, one tile per catalogue family in the
  same tile format with neutral sample content, grouped as `motifs.md` is. "Browse" opens it
  instead of listing names. Custom and universe-inspired motifs are not in it; "Show me"
  covers those. `motifs.md` stays the source of the catalogue: a family added there gets a
  tile in the same commit, and `tests/run.mjs` checks every family has one.

`motifs.md`'s "four ways in" and §DESIGN's sentence naming them become five.

### A release theme (the owner's proposal, 2026-11-12; name not chosen)

From v4, each major version carries a **theme**: a codename and a look, the way Android
releases were named. Themes need not follow one series or a number pattern; each major picks
its own. The owner is still choosing v4's (fiction or anime, or a nod to what the standard is
built on; "Super Saiyan 4" was given as an example of the idea, not as the pick).

Decided: themes start at v4, and the README is designed in the theme.

The agent's advice, not yet accepted or declined:

- **The theme lives on the surface, never in the rules.** README, CHANGELOG heading, release
  notes, the motif gallery page, the startup check's one-line banner. Rule and skill wording
  stays plain: it is loaded every session and must be understood by an agent that has never
  heard of the theme (§NAMING: name things by what the reader understands).
- **Version numbers stay the reference.** "v4.0.0" is what a project records; the codename
  sits beside it and is never the only identifier.
- **Inspired, never copied** (§DESIGN's own rule for universe-inspired motifs). This
  repository is public. A codename that nods to a series is low risk; that series' logos,
  character art or screenshots in the README are someone else's property. The look is
  original work drawn in the spirit of the theme.
- **The theme goes through `design-motif`** like any project's look: brief, sample tiles,
  mockup loop, lock. A good first real use of "Show me".

### The machine inventory (the owner's proposal, agreed 2026-11-12)

A project does not know what the machine it runs on has unless the owner says so each time.
The inventory fixes that, the way the `Studio credit:` line does for the studio: it is about
the owner's machine, so it lives in the owner's own files, not in a project.

- **Where:** `~/.claude/machine.md`, imported from `~/.claude/CLAUDE.md`, so every local
  session on that machine loads it. One file per machine.
- **Holds:** installed tools with version and what each is good for (ffmpeg, yt-dlp,
  Blender, ComfyUI, Ollama, LM Studio, whisper.cpp and the like); the hardware that matters
  (GPU and its memory); a short list of tools not installed but worth suggesting. Never a
  credential.
- **Kept true by a skill** (`machine-inventory`), which probes the machine and rewrites the
  file, run when the owner installs something or asks. A hand-kept list goes stale.
- **The rule, in the core:** before proposing a tool for media, AI or file work, read the
  machine file. Prefer what is installed; if nothing fits, suggest from its list; then search.
- **Cloud sessions** have no such file and assume nothing about the owner's machine.
- **A project that needs a tool** records it in its own `environment.md`, so a machine
  without it finds out at setup.

Built in phase 5. The README documents the file's format beside the `Studio credit:` line.

### §SECURITY additions (draft wording, for the owner's approval before it is written in)

> - **No token in code a browser receives.** A front-end bundle is public. Anything it holds
>   is published, however the repository is set.
> - **A token is as small as its job.** Fine-grained, scoped to the repositories it needs,
>   with an expiry. Never a classic token with account-wide `repo` scope in a script or app.
>   `environment.md` records each token, its scope and its expiry.
> - **The default branch is protected** where the plan allows it: changes arrive by pull
>   request, and force pushes are off.
> - **A workflow declares the least `permissions` it needs**, and a repository that needs no
>   Actions secrets has none.
> - **An unexplained change under `.github/workflows/` is an incident until proven otherwise.**
>   Do not run it, do not "fix" it; tell the owner first.

And in `relay` Step 4: list commits since the last checkpoint that touch `.github/workflows/`
or `.claude/settings.json`; any the session log does not explain go at the top of the report.

## Phases

Each fits one dedicated session and ends at a checkpoint on the working branch. None is
early-week sized except where marked.

1. **The split, no wording changes.** Move sections into the files above word for word; a
   read-only check that every non-blank line of v3.8.0 is in exactly one new file. Update
   `sync-standards`, the startup check, `sync-rules.mjs`, `install-skills.mjs`, the templates
   and `tests/run.mjs` (version agreement across the set, links, the import lines).
2. **Profiles.** `rules/game.md` (#25, #28), #30, #32; the non-application file; the
   on-demand trigger for AI (#23 rides here).
3. **Documents and sessions.** #33, #26 with the settings hook, #27, #31, #24; the STATUS
   migration; evals for relay-after-compact and the STATUS split.
4. **Motif previews.** The "Show me" way in (skill, `motifs.md`, §DESIGN, an eval case that
   it drafts before asking for a pick), then the gallery. The gallery is the long part; if
   the session runs short it ships with the families done and the test lists the rest.
5. **Security, the Process X document, small fixes.** The §SECURITY rules and relay's
   workflow check; #29; #20, #21, #22 (these three are small enough for early in a week);
   the machine inventory (skill, core rule, README).
   After this phase every open proposal is handled.
6. **Process X on the standard itself**, inside v4.0.0 and before the release (the owner's
   order: proposals, then the audit and its adjustments, then release). It may take more
   than one session: the audit is one, the picks' build another. Run as `process-x.md`
   says, read for a standard rather than a product:
   - **Audit, read-only:** every section of the core and profiles, every skill, template,
     script, hook and eval. Delivered as a ranked list the owner can pick from, each finding
     one of: keep, cut (no project relies on it), merge (said twice), move to a skill
     (procedure, not rule), tighten (same rule, fewer words), or missing. Evidence for each:
     which projects use it, which issues or decisions it came from, its size.
   - **The owner picks.** Nothing changes before that.
   - **Build the picks**, one commit per finding, so each can be reverted alone. A rule
     never lives only in a skill: the core keeps its one line.
   - Record before and after sizes for each file.
7. **Theme and release.** The themed README through the motif loop; CHANGELOG with a v3 → v4
   migration section, `adopting-the-standard.md`, `docs/maintainer.md`. Run the evals by
   hand. **Pilot before release:** sync one project of each kind from the working branch (a
   web project, a Node tool, `godot-toll`, a non-application repository), fix what they
   find, then `git CPR`.
